# SuperCardAI Frontend Plan

**Status:** Draft for review, 2026-10-01
**Covers:** P0-15 (Arabic-first customer UI) and the UI half of P0-16 (minimal admin operations)
**Sources:** `../SuperAI_Backend/docs/` — API_CONTRACT.md (binding), ERROR_CODES.md, IMPLEMENTATION_MODULES.md (launch rules), UI_UX_RESEARCH.md §12 (page brief), RADIO.md §2.1 (architecture sketch)

## 1. What we are building (launch scope)

The launch is **admin-funded**: no online payments, no self-service subscribe or top-up. So the UI_UX brief's P0-06 checkout, P0-07 payment result and P0-11 add-balance pages are **out**; wherever they would appear we show "contact the team" instead.

Binding rules from the backend contract:

- Auth is Supabase GoTrue directly from the browser (`@supabase/auth-js`), email + password, email confirmation required, sign-up sends `full_name`. API uses `Authorization: Bearer`, **no cookies**.
- Users see **modes** (`fast`, `professional`, …) with `labelAr`/`labelEn`, never provider or model names.
- Money is a **9-decimal USD string**. Never `parseFloat` for arithmetic; format for display only.
- UI text comes from the frontend, keyed by error `code`. Arabic first, RTL.
- Balance exists only while a plan is active; all of it expires when the plan ends.
- Chat is SSE over `POST` (`started` → `delta`* → `done` | `error`), with `AbortController` stop, `clientRequestId` retries, and `INSUFFICIENT_BALANCE.data.alternatives` → explicit **Switch mode** button, never auto-switch or auto-send.

**SPA mode notes**

- Enable with the Start Vite plugin's `spa: { enabled: true }`, and prerender `/` and `/plans`. The SPA shell is the fallback for every other route; the static host must rewrite unknown paths to it.
- **No server functions or server routes for API calls.** The browser talks to NestJS and GoTrue directly with the bearer token, exactly as API_CONTRACT §2 describes. That keeps hosting static and avoids a second backend.
- Auth guards run in route `beforeLoad` on the client, using the auth-js session; admin guard checks `GET /me → isAdmin`.
- Prerendered pages must not touch `localStorage`/session at render time; read the session only on the client.

**HeyAPI notes**

- `npm run api:sync` runs `openapi-ts`; output goes to `src/api/generated/` and is committed, never hand-edited. CI fails if it differs from a fresh generation.
- The fetch client gets one configured instance: `baseUrl` from env, an auth callback that injects the current GoTrue access token, and a response interceptor that refreshes once on `401` and handles `ACCOUNT_SUSPENDED` / `ACCOUNT_DELETED`. Errors are typed as the API error body `{ statusCode, code, message, details?, data? }`.
- Configure pagination keywords so the infinite-query helpers cover both cursor styles: `cursor` (conversations) and `before` (messages, balance activity, admin ledger).
- After the chat stream's `done`/`error`, invalidate or patch caches using the generated `queryKey` helpers (`me/balance`, conversation list, messages).
- Naming depends on backend operationIds (currently `ConversationsController_list` → `conversationsControllerList…`). See §6 item 6.

## 6. Backend gaps to raise

Found while mapping pages to the OpenAPI file (rechecked 2026-10-02 after the chat release; items 1–4 are still open):

1. **No delete or rename conversation** endpoints. The client requirements list delete; UI_UX lists rename as optional P0.
2. **`MessageDto` has no cost or token fields.** Per-message USD cost is only in the live `done`/`error` event, so it disappears on reload. UI_UX wants cost per response and an expandable token breakdown.
3. ~~No pre-send estimate.~~ **Decided 2026-10-02: no estimate before sending.** The UI shows the actual cost after each answer; an estimate appears only inside the `INSUFFICIENT_BALANCE` warning, where the API provides it.
4. **`ActivityEntryDto` has no conversation or mode link**, so the balance page can't show "which conversation/mode" per charge as the brief asks.
5. **Admin usage view and overview counts** (backend 10.5) not yet available.
6. **Cleaner operationIds** (nice to have): NestJS defaults like `ConversationsController_list` produce long generated names. An `operationIdFactory` in the Swagger setup (e.g. `conversations_list`) or explicit `@ApiOperation({ operationId })` gives `conversationsList` / `conversationsListInfiniteOptions`. Better to change this **before** the frontend depends on the names.
7. **Chat endpoint's error responses are typed as `text/event-stream` in OpenAPI.** `@ApiProduces('text/event-stream')` on `ChatController.send` applies to every response, but errors are JSON (API_CONTRACT §6.2). Fix: declare the stream content type on the 200 response only. Until then `api:sync` excludes `ChatController_send` from SDK generation (the stream client is hand-written anyway) and its errors are typed with `ApiErrorResponseDto` by hand.
8. **Answers are capped at 4,000 output tokens** (B2 decision). Long answers end `partial` with `finishReason: "length"`; the UI shows a clear "answer was cut" note. Raise it if the cap is too low for Professional mode.
9. **Contact channel** for "ask for a plan / more balance": need the actual WhatsApp/email/phone (config value).

## 7. Conventions (summary; full version goes in CLAUDE.md after F0)

- Generated API types are never hand-edited; run `npm run api:sync` after backend `api:export`.
- No string literal copy in components; all text through i18n keys. Error UI always by `code`.
- Money: strings in, strings out; arithmetic only via the decimal helper.
- Tailwind logical properties only; icons that imply direction (arrows, send) flip in RTL.
- Each page/component ships with loading, empty and error states and a test.

## 7b. Mobile readiness (Capacitor later)

A future iOS/Android app is planned as the **same SPA build wrapped in Capacitor**. Nothing native is built now, but F0–F2 follow these rules so the wrap is cheap:

- **One static build, two targets.** The mobile target skips the prerendered landing page and starts at sign-in/chat. A build flag (`VITE_TARGET=web|mobile`) only switches entry route and hides web-only content. Make sure the SPA shell is emitted as `index.html`, which Capacitor's `webDir` needs (check the Start SPA output setting during F0).
- **Absolute API and GoTrue URLs from env.** No relative `/api` paths or dev proxies baked into runtime code.
- **Session storage behind an adapter.** auth-js gets a custom `storage` (it accepts async `getItem`/`setItem`/`removeItem`): `localStorage` on web, **`@capacitor/preferences`** on mobile. Preferences saves to native storage (UserDefaults on iOS, SharedPreferences on Android), which the OS doesn't clear the way it can clear the WebView's `localStorage`. It is not encrypted. That's acceptable for launch since it sits in the app's private sandbox. If a security review requires encryption, swap the adapter to a Keychain/Keystore plugin with no other changes.
- **Streaming sits behind a transport interface.** The chat layer depends on `ChatStreamTransport.send(request, signal) → AsyncIterable<ChatEvent>`, not on `fetch` directly. Default implementation: the WebView's own `fetch` + `ReadableStream` SSE parser, with `CapacitorHttp` left disabled (its fetch patch buffers the whole response, the cause of Capacitor issue #6582). If a device spike shows WebView buffering, add a native implementation (e.g. a stream-HTTP plugin) on mobile only, with no chat-logic changes. Any transport must support POST + `Authorization`, cancel on abort, and must **not auto-reconnect**: the API has no resume, and a reconnect would re-POST the message (at best `DUPLICATE_REQUEST`).
- **Device spike before mobile work starts:** run the chat stream on a real iPhone and Android device through a production-like proxy; check deltas arrive incrementally, Stop aborts, and background/resume recovers.
- **App lifecycle.** iOS suspends the WebView in the background, which drops the stream. The backend treats that like Stop (keeps a `partial` answer), so on app `resume` we refetch the open conversation's messages and balance. Put this in the chat layer as a "page became visible again" hook that web uses too.
- **Layout.** Safe-area insets (`env(safe-area-inset-*)`), a composer that stays above the on-screen keyboard, and `100dvh` instead of `100vh`. Touch targets ≥ 44px (already a WCAG goal).
- **Links in emails.** Confirmation and password-reset links need deep links (Universal Links / App Links) into the app, plus matching GoTrue redirect URLs.

Backend and policy items for when the app starts (not launch blockers for web):

- Add `capacitor://localhost` (iOS) and `https://localhost` (Android) to `CORS_ORIGINS`, and the app's redirect URLs to GoTrue.
- **App Store rules:** in-app account deletion is required for apps that allow sign-up (backend has no delete yet, P1-09). Selling balance or plans inside the app generally requires Apple/Google in-app purchase, and pointing users to outside payment is restricted by storefront. The mobile build's "contact us to subscribe" wording needs a policy check. A plain website wrapper can be rejected for minimum functionality; plan a few native touches (push notifications, share sheet).
- Consider a **PWA** (installable web app, no store review) as a cheap first step before the store apps.

## 7c. Brand identity is configurable (white-label)

Decided 2026-10-02: the product ships as **بيان (Bayan)**, but the identity must be swappable so the platform can be sold to another customer without code changes.

- **Brand layer (per customer):** name (Arabic/English), logo + favicon + app icons, primary/brand color ramp, accent for the brand mark, optional font override, contact channels, legal links. Lives in one `brand.config.ts` + a theme CSS file selected at build time (`VITE_BRAND=bayan`); later it can be served at runtime.
- **Semantic layer (fixed):** mode colors are assigned per mode key from a palette (admins can add modes), and status colors (success, warning, danger) never change per brand, so every brand keeps passing contrast.
- No brand name or color is hard-coded in components or copy: copy uses `{{brandName}}` interpolation; components use tokens only.
- The design system in Stitch is named generically; brand values are one swappable section of DESIGN.md.

## 8. Decisions needed

1. **TanStack Start (SPA mode) vs Next.js** (RADIO §2.1 says Next.js). Recommendation: TanStack Start in SPA mode with prerendered public pages, for the reasons in §2.
2. **Repo:** `SuperAI_frontend/` currently sits inside the parent `SuperCardAI` git repo (branch `master`, no commits). Recommendation: its own repo, like the backend, as a **single app, not a monorepo**. Capacitor wraps the same build, so mobile later means adding `capacitor.config.ts` plus the generated `ios/` and `android/` folders to this repo. Platform differences live in `src/platform/` (storage, stream transport, app lifecycle, deep links) behind interfaces chosen at build time (`VITE_TARGET`). Admin routes stay in the same app, lazy-loaded, and excluded from the mobile build. Revisit a pnpm-workspace monorepo only if a second, separately built app appears (a React Native app, a standalone admin app, or a marketing site on a different stack). Keep `src/api`, `src/i18n`, `src/lib` free of imports from routes/features so they can move into packages then without rewrites.
3. **Shared design:** is a designer delivering a Figma/design system, or do we build from placeholder tokens and refine?
4. **Hosting** for the frontend (static host + CDN; must not buffer SSE on the API side — that's the backend's proxy).
5. Answers to the backend gaps in §6, especially 2 and 3, which change the chat UI.
